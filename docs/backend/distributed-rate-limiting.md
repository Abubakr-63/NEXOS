# Phase B4: distributed authentication rate limiting

Implemented 2026-10-28. No frontend, database schema, B1 hashing, B2 registration transaction, B3 cookie policy or API route changes. Other roadmap phases remain out of scope.

## Original implementation audit

The global Nest ThrottlerGuard used its default in-memory storage. Installed throttler behavior was inspected before implementation:

- 60 requests per controller handler and normalized client IP, in a rolling 60-second window. The 61st hit triggered a 60-second block; denied requests did not extend that block.
- Tracker came from Fastify req.ip, normalized by the installed throttler: mapped IPv4 addresses collapse to IPv4, ordinary IPv6 addresses aggregate to /64, loopback stays distinct as ::1.
- Keys were SHA-256 over controller/handler/throttler name and tracker. Each process maintained separate hit/expiry/block state, lost on restart. Multiple replicas therefore multiplied the effective allowance.
- No account/email dimension existed. All attempts, including validation failures, counted before the controller. Default HTTP 429 and rate-limit headers were generated by Nest and wrapped by the existing error filter.
- Redis existed only as configured BullMQ infrastructure; the API neither used nor checked it. Readiness checked PostgreSQL only. There was no shared-limiter outage policy.

## Scope and atomic algorithm

POST /api/v1/auth/login and POST /api/v1/auth/register now use RedisAuthLimiter through ApiRateLimitGuard. Other routes keep the existing local ThrottlerGuard with unchanged thresholds. In particular, logout/revocation are not made dependent on Redis, and public reads in a running process remain available during a Redis outage.

Threshold/window/block remain **60 / 60 seconds / 60 seconds**, independently per action and normalized IP. No account-based lockout or threshold tightening was introduced.

One Lua EVAL operates on one Redis sorted set per action/identity. Redis executes it atomically across clients/processes. It uses Redis TIME, not API process clocks:

1. Return the remaining block duration if an unexpired block marker exists. Denials never extend its TTL or append members.
2. Remove expired accepted hits and count remaining members.
3. When already at 60, add one block marker scored with its expiration and set a 60-second TTL. Return denial and retry information.
4. Otherwise add one uniquely identified accepted hit, set a 60-second TTL, and return remaining allowance and earliest capacity-reset time.

The set holds at most 60 accepted-hit members plus one block marker. Expiry is at most 60 seconds after the last accepted hit or block creation. An expired block resets state. A single script covers check/increment/prune/block/expiry, so simultaneous requests cannot exceed the allowance. Redis script errors are not database-style rollbacks; any partial mutation still cannot grant an authentication request because errors fail closed. No non-atomic client read/modify/write or application-side timestamps are used.

## Keys and privacy

Default key structure:

`nexos:ratelimit:auth:v1:<login|register>:<sha256(normalized client IP)>`

RATE_LIMIT_NAMESPACE overrides the deployment prefix. It must be identical across all API replicas and unique among deployments sharing Redis. Allowed syntax is 1–80 letters, digits, colons, underscores or hyphens. It is configuration, never user input. A separate `<namespace>:probe` key exercises script/write availability for startup/readiness, with a one-second TTL and at most two members.

The existing public normalizeIp function from Nest throttler is reused, preserving IPv4/mapped IPv4 and IPv6 /64 handling. Fastify req.ip remains governed exclusively by B3's explicit trustProxy configuration. No raw X-Forwarded header parsing is added. Invalid resolved addresses fail closed. Forwarded-header spoofing from an untrusted peer does not create new buckets.

No password, email, username, session token or password-derived secret appears in limiter keys/members/logs. Members are request-independent random UUIDs and timestamps, not authentication credentials. IP digests are pseudonymous, not anonymous; address spaces can be guessed. They still require appropriate operational access controls.

## Redis and failure policy

The API now directly declares **ioredis 5.11.1**, already present transitively through BullMQ. No new client family, worker, Redis deployment definition or rate-limiter plugin is introduced.

- REDIS_URL supports redis/rediss, encoded credentials and a numeric database path. Production requires an explicit URL. Local default is redis://127.0.0.1:6379. Invalid URLs/credential encoding/namespace produce sanitized configuration errors.
- One connection per API process. Connection and command timeouts are one second; offline queuing and replay of unfulfilled commands are disabled; maxRetriesPerRequest=0. Reconnection attempts use bounded backoff up to one second. A lost reply may conservatively count an attempt without admitting it; it is not replayed to grant additional attempts.
- Startup connects and executes the real script on the short-lived probe key. Failure aborts startup; the bootstrap closes application resources. No silent in-memory fallback exists for login/register.
- During outages, login/register return the existing error envelope with HTTP **503**, sanitized message Authentication temporarily unavailable. Try again later., and Retry-After: 1. Raw Redis errors are not logged or returned.
- A running API's /ready returns 503 when PostgreSQL or the Redis script probe fails; /health remains liveness. Public reads and logout retain local limiting and can continue. Dependency-wide readiness means an operator removing all unready instances from a load balancer may also make public reads unavailable; service routing policy is external to this application.
- Recovery reconnects automatically. Surviving Redis counters remain effective across API reconnects/restarts. A Redis data loss/failover that loses acknowledged writes can reset allowances; atomicity on one primary is not a durability guarantee.
- Standard HTTP **429**, Retry-After (integer seconds), and X-RateLimit-Limit/Remaining/Reset accompany denials. The existing error envelope and default throttler message are preserved. Reset is a relative seconds estimate, consistent with the previous header convention.

## Deployment and resource requirements

Use the existing Redis service. The local environment had no running Redis/binary, so the configured Redis 7 Alpine service image was started through available Podman on loopback, using a persistent data volume:

```sh
podman run -d --name rom-hub-redis -p 127.0.0.1:6379:6379 \
  -v rom-hub-redis-data:/data docker.io/library/redis:7-alpine \
  redis-server --appendonly yes
```

For an existing container, use `podman start rom-hub-redis`; Docker Compose users can continue `docker compose -f infrastructure/docker/compose.yaml up -d redis`. No PostgreSQL data or running Redis database was flushed or reset. The test network proxy described below does not stop this Redis service.

Before production:

- Configure the same Redis endpoint/database and RATE_LIMIT_NAMESPACE across replicas. Finish a coordinated rollout/drain old in-memory-only API processes; a mixed old/new fleet cannot enforce one aggregate limit. Keep the namespace stable across ordinary restarts.
- Use private Redis access, authentication/ACLs, and rediss when transport needs TLS. Operators provision certificates/credentials; no secrets are embedded in the repository. The client is for a single Redis endpoint; Redis Cluster/Sentinel discovery is not configured by this phase.
- Use **noeviction** and a measured Redis maxmemory budget. Evicting counters can bypass limits; this implementation does not dynamically change or certify server eviction configuration. Under noeviction, command/OOM errors fail authentication closed. A shared BullMQ instance must retain enough headroom for both workloads. Do not silently change a shared server's memory policy from the API.
- TTLs and per-set cardinality bound retained state, but do not impose a global limit on distinct active IPs. High unique-IP traffic can still consume substantial memory inside a window. Size/monitor Redis memory, latency, key count and eviction/OOM metrics; add edge network/request controls as required. Local Redis uses its existing default noeviction policy; production sizing was not load-tested.
- Protect the B3 proxy chain. Incorrectly trusted client-controlled forwarding headers allow bucket rotation; proxy misconfiguration can also group all users into one shared address and cause denial of service.
- Per-IP limits constrain multi-account attempts from one address but do not stop a distributed botnet. Account-aware abuse protections require a separately reviewed policy; adding them here would change thresholds, lockout/enumeration behavior and legitimate-user availability. Registration's existing 409 and login's generic 401 semantics are unchanged.

## Automated verification

Real integration coverage uses the existing local Redis and PostgreSQL, not a mocked Redis:

- 120 simultaneous consume calls across two independent Redis clients: exactly 60 admitted; bounded sorted-set cardinality and TTL.
- Actual key expiry/reset, rolling-window hit pruning, mapped IPv4 equivalence and IPv6 /64 equivalence/separation.
- Two independent API subprocesses with one test namespace: 80 simultaneous attempts per login/register action produce exactly 60 admitted-to-validation (400) and 20 rate-limited (429). Spoofed forwarding headers cannot split the untrusted socket peer's bucket. Invalid bodies avoid creating accounts or exercising expensive password hashing in this threshold test.
- A test-only TCP proxy forwards to real Redis. Destroying/reopening this network path exercises actual client disconnect/reconnect behavior while preserving the underlying server/data. Both APIs return controlled auth 503 and readiness 503; public reads and logout continue; recovered counters still deny blocked requests.
- An additional API process exits with failure and a sanitized startup message when that Redis path is unreachable.
- Existing B1/B2/B3 integration and authentication E2E regressions remain in the suite.

Unit tests validate Redis URL/namespace safety without external services. E2E and integration runs use unique test namespaces to avoid exhausting each other's real shared counters; keys expire naturally. The network-fault integration requires a non-TLS local Redis test URL. No certificate, Redis failover/data-loss, production ACL, eviction or production-load tests are claimed.
