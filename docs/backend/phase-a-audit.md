# Backend Phase A audit

Reviewed 2026-10-28. Scope: existing NestJS/Fastify API, Prisma/PostgreSQL schema and three migrations, contracts, catalog seeding, BullMQ foundation worker, configuration, API documentation and automated tests. This is a source and local runtime audit, not a penetration test or production certification. No schema, authentication design, response contract, frontend, branding or infrastructure topology was changed.

## Architecture and confirmed behavior

- `apps/api/src/main.ts`: NestJS 11 + Fastify 5; `/api/v1` routes; cookie/Helmet plugins, 32 KiB request body limit, exact-origin credentialed CORS, cookie/authorization log redaction, OpenAPI, shutdown hooks. Fastify adapter already translates malformed/oversized/unsupported bodies to 400/413/415; this was tested, not inferred to be missing.
- `apps/api/src/app.ts`: a single AppModule, Database/Accounts providers and three controllers. The Database provider owns one Prisma client/pool per API process, connects and checks required tables/columns at startup, disconnects on shutdown. `/health` is liveness; `/ready` probes real PostgreSQL. No per-request Prisma clients were found. Pool sizing/timeouts currently come from Prisma/connection URL defaults.
- Passwords: salted asynchronous scrypt, constant-time equal-length digest comparison, dummy derivation for unknown email. Sessions: 32 random bytes, SHA-256 token digests at rest, HttpOnly/SameSite=Lax, Secure when NODE_ENV=production, seven-day absolute expiration checked on every authenticated request. Login rotates the presented session; logout and owner-scoped revocation remove server-side tokens. Email verification/recovery/OAuth are not active features.
- All current mutations check exact WEB_ORIGIN and JSON content type. Authenticated ROM project operations scope IDs to owner; foreign ownership returns 404. Account role input is rejected. Audit endpoint requires ADMIN. No user directory or account-deletion API exists.
- `packages/contracts/src/index.ts`: strict account/configuration/save Zod schemas and bounded device/legacy queries. Project current JSON + revision snapshots are written atomically. Compare-and-swap rejects competing writers with 409. Existing schema-version-1 data remains supported, including unchanged deprecated references.
- PostgreSQL: three applied migrations; unique email/username/token hash, project owner FK/index, unique project/revision number, catalog identity constraints and base identity uniqueness. User deletion cascades to sessions/drafts/revisions; there is no exposed deletion route. No destructive migration is warranted by this audit.
- Curated catalog: seven real device families, eleven exact variants, two source bases. Legacy demos remain deprecated, not deleted. Catalog/source identification never grants build support. Compatibility remains UNKNOWN; builds return 503 without enqueueing.
- BullMQ worker: connectivity probes only, concurrency two, unsupported jobs throw, signal handler closes worker. Redis is separate from API persistence. No build producer, compiler, upload endpoint, artifact verifier or artifact delivery exists. Storage/search compose services are optional local scaffolding, not integrated features.

Known architecture weakness: controllers/services/database access are concentrated in `app.ts`. This is manageable at current size, but feature growth should extract Accounts, Catalog and ROMProjects modules without changing behavior. This is a MEDIUM maintainability recommendation, not grounds for a rewrite. Optional compose storage/search credentials are development defaults on loopback; these services must not be promoted to shared deployment unchanged.

Password policy references: [Node 22 scrypt defaults](https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Throttling deployment behavior: [NestJS official rate limiting](https://docs.nestjs.com/security/rate-limiting). Parser handling checked against [Fastify errors](https://fastify.dev/docs/latest/Reference/Errors/) and live requests.

## Existing API contracts and stable structure proposal

Retain `/api/v1`; no new speculative endpoint is implemented. `items` lists, `user` authentication responses, direct project objects and `error: {status,message,requestId}` are current contracts. Preserve these envelopes in v1; do not globally wrap or rename them. Zod errors use message arrays; HTTP errors use strings. Document both rather than silently forcing a new error shape. Nest POST currently returns 201, including login/logout/validation; record this before proposing different semantics.

| Existing routes (under /api/v1)     | Authorization / validation                                  | Current result                                                                     |
| ----------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| GET health, ready                   | Public, throttled                                           | Liveness/readiness; ready returns 503 on database failure                          |
| POST auth/register, auth/login      | Exact Origin + JSON; strict shared schemas                  | Public user projection and HttpOnly cookie; 400/401/409 as applicable              |
| GET auth/me, auth/sessions          | Valid unexpired session                                     | `{user}` or `{items}` without password/token hashes                                |
| POST auth/logout                    | Exact Origin + JSON; idempotent without valid session       | `{success:true}`, server token removed and cookie cleared                          |
| DELETE auth/sessions/:id            | Origin + JSON + session; owner filter                       | Idempotent `{success:true}` even for absent/foreign IDs                            |
| GET manufacturers                   | Public                                                      | `{items:[{id,name}]}`, active real devices only                                    |
| GET devices                         | Public; shared bounded query schema                         | `{items,total,page,limit}`, exact variant/source metadata; UNKNOWN                 |
| GET android-bases                   | Public                                                      | `{items,explanation}`, source availability, no compatibility grant                 |
| GET legacy/catalog-projects[/:slug] | Public; list query validated, slug treated as exact lookup  | Existing public catalog; not owner drafts. Detail only includes PUBLISHED releases |
| GET projects                        | Session                                                     | Latest 100 owned records; `{items}`                                                |
| POST projects                       | Origin + JSON + session + strict config + active selections | Owned draft + snapshot #1; unselected/unconfigured allowed                         |
| GET projects/:id                    | Owner or 404                                                | Current configuration, variant/base, compatibility                                 |
| PATCH projects/:id                  | Origin + JSON + owner + `{configuration,revision}`          | Atomic CAS/snapshot; stale revision 409; unchanged legacy selections retained      |
| GET projects/:id/revisions          | Owner                                                       | Latest 50 snapshots; `{items}`                                                     |
| POST projects/:id/validate          | Origin + JSON + owner                                       | Persisted configuration validation, currently UNKNOWN                              |
| POST projects/:id/builds            | Same validation/ownership                                   | Always 503; no job created                                                         |
| GET admin/audit                     | ADMIN session                                               | Latest 50 events; `{items}`                                                        |

No `/users` CRUD, preset, app, kernel, upload or build-status API exists today. Current user identity belongs at `auth/me`; do not add a user directory without a use case. Build configuration is schemaVersion-1 JSON on projects, not a separate CRUD resource. Presets/apps are bounded intentions in the config schema; kernel is literally `unconfigured`.

Next contract work: publish reusable request/response/error schemas from contracts, include security/parameters/examples in OpenAPI, pin validation semantics and add response-schema tests. Future pagination may use optional cursors with explicit continuation metadata after review. Preserve stable existing IDs and ownership boundaries.

## Phase A changes and verification

Files changed in this task only: `apps/api/src/config.ts`, `apps/api/src/app.ts`, `tests/infrastructure.test.ts`, `tests/api.integration.ts`, and this report. Prior working-tree frontend/catalog/branding changes were preserved. No dependency, migration, database reset, account deletion or project reassignment was introduced. Tests create uniquely named test accounts/fixtures and clean up only their own account/project fixtures; the existing seed test safely upserts reviewed catalog metadata and preserves legacy references.

Verification results are recorded after the final run below. Production policies, fault-injected registration rollback, Redis connectivity, TLS/proxy topology, outage recovery, backup restoration and load behavior were not tested in this local phase. No public-production readiness claim is made.

Executed successfully:

- `pnpm typecheck` and `pnpm lint` (root and workspace checks).
- `pnpm test`: 12 unit tests, including new missing-database-path validation cases.
- `pnpm build`: all seven workspace build tasks successful; no new migrations.
- `pnpm test:integration`: 3 tests with actual PostgreSQL/API, including session/CSRF/RBAC/ownership, catalog/legacy-reference preservation, concurrent saves, expiry, parser errors, CORS, throttling, plus sanitized error-log correlation.
- `pnpm test:e2e`: 6 Chromium tests through the Next proxy, including registration/session/logout, persistent real-device drafts, build rejection and existing accessibility/navigation flows.
- `pnpm db:status`: three migrations applied, schema up to date.
- `git diff --check`: clean. Live frontend-proxied `/api/v1/ready` returned 200 after restoring the development API.

The targeted log test uses the built exception filter with an isolated HTTP context and verifies generic output/no secret reflection; it does not claim to induce a PostgreSQL outage. Registration-failure atomicity remains a separate unexecuted fault-injection test proposal.

Recommended next phase: **Phase B — reviewed authentication and deployment hardening** (H1–H4), followed by schema-backed OpenAPI/response contracts. Keep product/compilation expansion paused until these foundations have acceptance tests and an agreed deployment model.
