## 1. Executive decisions

No business endpoint, v1 request validator, response shape/status, cookie, ownership rule, limiter, database schema/index, existing data or secret was changed. The documentation is intentionally upgraded to **OpenAPI3.1** to retain JSON Schema2020-12 recursive JSON/nullability accurately. Existing Swagger tooling/UI supports it; consumers of the document must support3.1. Operation IDs are now explicit meaningful names rather than autogenerated controller names; external SDK regeneration may rename methods. No3.0-only downstream consumer was identified in this repository; external documentation tooling compatibility requires operator review. This is a documentation-format update, not a v1 API version change.

## 3. Shared schema integration

`apps/api/src/openapi.ts` uses Zod4.6.6's installed `toJSONSchema` API and the existing Nest Swagger document generator. Request schemas use **input** conversion; responses use **output** conversion. ROM configuration therefore retains strict nested fields, required schemaVersion1, exact enums/literals, bounded/deduplicated applications, revision rules and optional input description versus required normalized output description. Nullable device/base relations and timestamp/string/null fields are retained.

Named common schemas use component references. Zod's recursive raw JSON definitions are rebased into their owning component, so list configurations/revision snapshots remain arbitrary JSON rather than falsely becoming normalized ROMConfiguration. All references are locally resolved/tested. Plain create/update and enriched detail responses remain different components. Public user/session projections exclude email/password hashes and token digests. Password exists only as a writeOnly request field; no real password/token/cursor/secret example is exported. The representative default draft example is taken from shared defaultConfiguration.

Small **documentation-only adapters** cover named converter gaps:

- /i on the existing ASCII email regex is represented with equivalent case-inclusive character ranges, with lowercase normalization described.
- Trimmed string bounds apply after trim; generated input patterns permit surrounding whitespace and document normalized lengths rather than falsely rejecting valid padded input. NUL restrictions are represented.
- Custom integer predicates become integer schema types; application duplicate refinement becomes uniqueItems.
- Cursor mode's bounded decimal string limits/defaults are derived from the shared parsed bounds, including trim and raw digit restrictions. The undefined legacy discriminator is described separately, not replaced with an invented required mode.
- Existing controller-only opaque path/control-character/manufacturer guards are descriptive metadata, exercised by actual HTTP tests. They were not moved or rewritten solely for documentation.

This does not install JSON Schema validation into request handling or change Zod acceptance. The ordinary pre-migration corpus is checked against both shared Zod and document schemas. Runtime validators remain authoritative for transforms, custom code, database selection/ownership and cursor validation.

**Known representation limits:** JSON Schema string lengths/regex engines count Unicode differently from JavaScript UTF-16 checks; the document describes runtime UTF-16 semantics with extensions rather than modifying validators. Legacy numeric query parameters are documented as parsed bounded integers, with existing Number coercion described; noncanonical raw forms such as hex/exponent can normalize. Standard per-parameter schemas cannot enforce “ignore limit/cursor without mode,” authorization-first ordering, FK availability or opaque cursor scope/expiry. These conditional rules are explicit descriptions and real HTTP tests, not false promises of complete client-side static validation. No schema constraints were disabled to force a test pass.

## 4. Errors, security and pagination

Existing application envelope stays `{error:{status,message:string|string[],requestId}}`. Literal-status components cover400/401/403/404/409/429/500/503; other existing parser413/415 use the general APIError schema. The400 response additionally allows the **existing native RouterError** for early malformed URI failures. There is no universal envelope migration.

Protected operations explicitly document401/403; owners retain foreign/missing404. Bodies/queries/path guards document400, registration/stale saves409, all controller throttles429 and appropriate dependency503. Unexpected/stored-data failures500 remain generic; descriptions do not expose SQL, stack, body, token or infrastructure details. Liveness is not incorrectly advertised as a DB/Redis readiness check.

Retry-After is represented for429 and authentication protection503, with seconds semantics and no automatic-write retry recommendation. Other503 causes need not include it. Auth201 Set-Cookie and logout clearing attributes are described without token values. Cookie scheme name/format, HttpOnly/Lax/Path/no Domain, production Secure and exact Origin/JSON/trusted HTTPS expectations remain unchanged. A Swagger page on the API origin cannot override the configured frontend Origin policy; rejected cross-origin mutations remain403.

Four cursor collections document both **strict legacy and opt-in response schemas** via oneOf; they cannot accidentally overlap because metadata is absent in the strict legacy shape. Projects retain legacy100/update-time order; revisions/audit50; sessions remain **unbounded without opt-in**. Opt-in defaults/maxima: projects100/100, sessions50/100, revisions50/50, audit50/50. Cursor ordering, live keyset consistency, deletions/expiry/new rows, limit+1/no count, opaque format,15-minute non-renewal, endpoint/user/project binding,400 invalid/expired/tampered behavior and final hasMore=false/nextCursor=null are described. No cursor encryption algorithm/key/payload internals or secrets are published in the spec.

## 5. Validation, HTTP evidence and deterministic export

- `pnpm openapi:export` rebuilds contracts/API and exports sorted deterministic `docs/api/openapi.json`; optional output path supported. Metadata generation does not initialize services, open a listener or query PostgreSQL/Redis. Existing environment wrapper is used; no secret is minted/rotated in configuration. The CLI uses controlled failure handling rather than Nest's default abort path.
- `pnpm openapi:validate` rebuilds and checks the checked-in artifact **without regenerating it**, so stale documentation fails. Standard `pnpm test` includes the same five specification tests after the normal build.
- Structural validation uses the vendored OpenAPI Initiative3.1 document schema (2021-04-15) acquired from `@apidevtools/openapi-schemas@2.1.0`, retaining its source/license. The spec host was unreachable; no package was installed. CI requires no schema-host network access.
- Existing Fastify Ajv8.20.0/ajv-formats provide validation. For Ajv's local dynamic-anchor fallback incompatibility, the default OAI `#meta` anchor is resolved to its equivalent local schema reference **in memory**, with alternate dialect overrides rejected. The fixture remains unmodified. Every payload component is additionally validated/compiled against JSON Schema2020-12; all local references resolve. This is a targeted validator for the generated default dialect, not a claim to validate arbitrary alternate-dialect documents.
- Negative tests prove that missing response descriptions, broken references and invalid schema types fail. Unique operation IDs/parameters and required path declarations are checked. Tests also compare the artifact byte-for-byte with fresh generation, repeat generation, and assert database/Redis initialization hooks are not invoked.
- Input corpus/parameter tests exercise actual shared validators, lowercasing/trim/refinement adapters, optional/default fields, cursor bounds and legacy parsed-number behavior. Explicit sensitive server-only property names are forbidden in public component definitions; raw stored JSON remains raw, not a claimed secret-filtering serializer.

The added real Nest/Fastify HTTP test validates the **served** JSON, YAML equality and all21 independently registered operations. Every checked HTTP response is validated against its documented schema and successful bodies against shared Zod without changing serialization. It exercises public catalogs/legacy detail, synthetic registration/login/rotation/session listing/revocation/logout, plain/enriched project operations, all four cursor variants, pagination continuation, malformed paths/query/body, empty/malformed JSON,413/415, invalid Origin, foreign404, admin403, duplicate/stale409, unavailable builds/readiness and sanitized stored-data500.

Both IP login/register429 are exercised with actual Redis admission and invalid bodies to avoid unnecessary KDF work. Account429 uses a synthetic absent identifier. Retry-After is checked. Controlled limiter/readiness method faults verify documented503 without disrupting shared infrastructure; the existing full suite separately tests Redis outage/recovery using its TCP fault proxy and account-store faults. New fixtures are isolated synthetic accounts/projects and legacy release metadata only, cleaned by exact unique identity. No existing user credential/token was used or existing account/project modified.

Development corrections are disclosed: an initial source-based exporter/test import lacked decorator metadata; compiled API artifacts now match the repository's existing test convention. A test-only type import pulled controllers into the root type graph without cookie augmentation; compiled-helper signatures resolved it. Ajv's default-anchor mismatch was addressed as above, not by removing payload validation. An injection test initially treated a JavaScript null payload as a body; sending literal JSON `null` correctly tests the ignored-body wire contract. These earlier failed runs are not counted as passing verification.

## 8. Remaining limits and recommendations

Phase C's scoped contract work is complete with the passing local checks above. The document is comprehensive for current operations, with the explicit semantic limits above; it is not a security firewall, production sign-off or proof of every possible input/transaction failure. The validator supports the generated default3.1 dialect; alternate dialects/tooling and older3.0-only consumers require separate compatibility work. Doc metadata must be updated alongside any future route/guard contract change; the inventory/snapshot/HTTP tests are intended to fail on drift.

C4 legacy truncation/unbounded sessions, index/search/count performance, raw stored JSON and revision-storage bounds remain documented—not “fixed by OpenAPI.” Enumeration, retention and production operational risks remain open from the final gate. Keep worker/compilation/artifact features disabled until their own reviewed phase.

Recommended next approval: a backend operational/performance and retention plan (reviewed indexes/query plans, session/audit bounds with compatible clients, deployment readiness evidence), or an explicitly scoped foundation feature proposal from the existing roadmap. Do not infer authorization to implement any of it. Public deployment needs its own evidence-based gate including actual TLS/proxy/private ingress, Redis/PG isolation/capacity, backups/restore, monitoring and abuse/load validation.

**Stop after C5. No subsequent phase or production deployment started.**
